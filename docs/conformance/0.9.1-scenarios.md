# 0.9.1 conformance scenario skeleton

**Status:** executable baseline complete — every scenario in the table below has paired
Kotlin/Rust adapters (or a documented single-agent/proxy exception; see the notes below the
table). `TLS-PROXY-01` now has a documented, executed recipe —
[tls-proxy-recipe.md](../tls-proxy-recipe.md), first run 2026-07-27 against `c7c6680` — with all
five checks passing: upgrade, bearer forwarding, certificate rejection, reconnect, and notification
delivery. Cases 1–4 are proxy properties and backend-independent; case 5 ran against the simulated
backend, so it is re-confirmed against the live peripheral on Rig A before the scenario is signed
off at the 0.10.0 hardware-validation gate.  
**Applies to:** Kotlin reference agent and Rust reference agent

Each scenario gains a shared expected trace and a Kotlin and Rust adapter. `baseline` is mandatory
for both agents; `operational` may remain implementation-specific with an explicit rationale.

| ID | Class | Scenario | Required outcome |
|---|---|---|---|
| AUTH-PRINCIPAL-01 | baseline | Two credentials reuse one stable client ID | No lease, operation, or warm resume crosses principal boundaries. |
| AUTH-REVOKE-01 | baseline | Revoke a credential during transport grace | Revoked credentials cannot resume leases. |
| LEASE-DISCONNECT-01 | baseline | Explicit disconnect | Immediate release; reconnect needs a new connect. |
| LEASE-GRACE-01 | baseline | Transport loss and quick same-principal resume | Warm lease resumes once within grace. |
| LEASE-GENERATION-01 | baseline | Retired and new generations race | A retired generation has no effect on the new one. |
| LEASE-DUPLICATE-01 | operational | Second live generation for one `(principal, stable client id)` | The duplicate is refused and the first generation is unaffected. Transport signalling is implementation-specific (see note). |
| VERSION-01 | baseline | Invalid or non-overlapping hello range | Close 1002/reason; client reports `INCOMPATIBLE_PROTOCOL`. |
| LIMIT-FRAME-01 | baseline | Oversized encoded frame | Rejected before decoder/resource growth. |
| LIMIT-OP-01 | baseline | Over-limit scan filters, write/descriptor values, and MTU | Rejected as `INVALID_REQUEST` before reaching the BLE backend. |
| LIMIT-STREAM-01 | baseline | Duplicate and excessive stream IDs | Replacement cleans old resources; limits are stable. |
| LIMIT-SLOW-01 | baseline | Slow reader and event flood | Bounded queues/tasks/registrations with visible overflow. |
| RECOVERY-01 | baseline | Failed replay prerequisite | Dependents skip and readiness becomes degraded. |
| SHUTDOWN-01 | baseline | Shutdown during transport loss | Local collectors retire; result reports cleanup outcome. |
| LIVENESS-01 | baseline | Silent peer or writer failure | One bounded cleanup sequence and no residue. |
| BIND-SECURITY-01 | baseline | Non-loopback without credentials | Startup fails absent named development override. |
| TLS-PROXY-01 | operational | Supported `wss://` proxy recipe | Upgrade, notifications, reconnect, and CA validation succeed. |

Resource budgets, fake-backend fixtures, and hardware-evidence links are added by their owning
workstream. A scenario is parity-complete only after both adapters execute the applicable trace.

**LEASE-DUPLICATE-01 transport signalling (operational).** Both agents enforce D3's "duplicate live
generations for one principal/client key are rejected", but signal it differently, and this is
accepted rather than aligned: the Rust agent rejects during the WebSocket handshake with HTTP `409`
(no upgrade completes), while the Kotlin agent completes the upgrade and then closes with code `1008`
and reason `REMOTE_BLE_DUPLICATE_SESSION`. Both outcomes leave the first generation untouched and
fold into the client's normal reconnect path (the duplicate never reaches a usable session), so the
observable contract — refusal without disturbing the incumbent — holds on both. Aligning the wire
signal would mean moving Kotlin's session acquisition into the pre-upgrade auth interceptor, adding
coupling to the most security-sensitive path for a cosmetic difference; it is deliberately deferred.

**RECOVERY-01 has no Rust counterpart (client-only, by design).** The reconnect reconciliation state
machine — readiness (`DEGRADED`/`READY`), the dependent-operation replay/skip decision, and the
`ReconciliationReport` — lives entirely in the Kotlin client SDK (`client-sdk`'s `DefaultAgentSession`).
There is no Rust client SDK in this repository for it to pair against; `agent-rs` is agent-only. This
scenario is therefore exempt from the "Kotlin agent + Rust agent" pairing pattern the other baseline
scenarios use, and is satisfied by the single Kotlin client-side adapter alone.

**SHUTDOWN-01's Rust adapter is a proxy, not the literal shutdown path.** The Kotlin adapter drives
the actual mobile-runner `stop()` teardown while a lease sits mid transport-grace. `agent-rs` has no
fake/mock `btleplug` seam — `disconnect_all` and `shutdown_signal` in `main.rs` talk to real
`btleplug` types, so they cannot be driven from a unit test the way `FakeBackend` drives
`server.rs`. `late_connect_after_connection_retirement_unwinds_radio_and_lease` instead proves the
same underlying property (a retired connection generation unwinds the radio link and releases the
lease, with the result reporting the cleanup outcome as `TransportLost`) through the one seam that
is testable without hardware. Closing this gap for real would mean adding a fake backend seam to
`main.rs`'s process lifecycle — tracked as a follow-up, not required to call SHUTDOWN-01 baseline-complete.

**AUTH-REVOKE-01 is new feature work, landed as part of this workstream.** Neither agent had any
runtime credential-revocation mechanism before — both `ClientCredentials` (Kotlin) and the Rust
credential map were static, built once at process startup. Both agents now carry a runtime-checkable
revoked-principal set consulted inside `authenticate()`/`ClientCredentials.authenticate`, so a
revoked principal fails re-authentication on its very next connection attempt — including a
same-stable-client-id resume within a lease's transport grace — before the registry is ever
consulted. Neither side wires this to an operator-facing trigger yet (Kotlin has no dashboard
mutation route for it; `agent-rs` has no admin endpoint or signal handler at all): the public API
(`ClientCredentials.revoke`/`unrevoke`/`isRevoked`, `AgentServer.revoke_principal`/
`unrevoke_principal`/`is_principal_revoked`) exists and is exercised by these conformance tests,
and wiring an actual trigger is a separate follow-up.
