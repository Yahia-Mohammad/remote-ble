20. **Mobile agents never configure an operator token, so they serve no dashboard** — **FIXED
    2026-07-30.** The previously recorded reason for it was also wrong: it was written up as
    structural, and `AgentConfig.operatorToken` is a plain `commonMain` field that `AgentModule`
    already forwards on every platform. `AgentApp` simply built `AgentConfig(bindHost = …)` and
    thereafter only `copy(authToken = …)`, so the credential stayed `null`, `dashboardRoutes` never
    registered, and `/` returned 404 — a wiring gap of the same shape as evidence follow-up 8, not an
    impossibility.

    **The fix:** an optional second masked field in the mobile UI. **Blank (the default) is exactly the
    old behaviour** — no credential, no routes, same 404 — so an existing install is unaffected;
    filled, the agent serves its read-only status surface to another device. `TokenStore` grew an
    `AgentSecret` parameter (default on the `expect`, so existing one-argument calls are untouched;
    Android's DataStore file name and client key unchanged, so a current install keeps its token).

    **Why two tokens is the right design, since the question was raised and deserves an answer on the
    record.** It is not that the dashboard is dangerous — it is read-only, four `GET` routes, no
    mutation endpoint by design. It is that **clients are deliberately isolated from each other on the
    op plane, and one shared token would undo that over HTTP.** Rig A case 3 proved the isolation on
    real radio: client B can scan, but every attempt against client A's leased device fails. The
    dashboard exposes every client's address, every lease and the activity log — recovering by HTTP
    exactly what the op plane refuses. Three supporting reasons, all already implemented: client
    tokens are distributed to app instances (many copies, higher leak odds) while the operator secret
    is one human's; `AUTH-REVOKE-01` revocation should be independent in both directions; and the two
    auth planes have separate brute-force limiters so an attack on one cannot exhaust the other's
    memory budget. `AgentWebSocketServer.init`'s `require` is the guard against collapsing them, and
    the UI now checks the same rule first so the user gets a message naming the field rather than the
    generic start-failure text.

    **The cleartext caveat is now fixed rather than documented.** The mobile agent binds `0.0.0.0`
    with no TLS proxy in front (that is Rig C's desktop recipe), and **Ktor's CIO server has no TLS
    support on Kotlin/Native at all** — verified by dumping the published iOS klib, which contains zero
    `ssl`/`tls` surface — so encrypting the mobile listener is not an option today. Rather than warn
    about it, the dashboard now answers **loopback only** unless remote access is explicitly opted
    into, mirroring `Main.kt`'s existing policy for a non-loopback bind. Non-loopback requests get
    **404** (not 403) *before* any credential is considered, so a correct token from the wrong origin
    still sees nothing and the surface is not advertised. Reach it from the device's own browser, or
    tunnel — `adb forward tcp:8080 tcp:8080` / `iproxy` — which keeps the secret off the network
    entirely. The UI switch appears only once an operator token is set, defaults off, and is
    deliberately **not persisted**: opening a cleartext high-privilege plane should be a per-run
    decision, not one inherited from a previous session.

    Worth keeping in view: **the client token has the same cleartext exposure** over `ws://` and always
    has. The operator token did not introduce a new class of problem, it raised the blast radius —
    which is why the fix is at the exposure layer rather than per-token. Rejected on the way:
    challenge-response or short-lived operator tokens, which would stop credential capture while
    leaving the response bodies (addresses, leases, log) in the clear — the appearance of a fix for
    real complexity.

    Two tests were added where the invariant lives rather than in the UI: an absent operator token
    leaves the routes **unregistered** (404, not 401 — the distinction that makes a phone agent's 404
    healthy rather than a symptom), and an operator token equal to a client credential is rejected at
    construction.

      `Default`; the Apple `Scanner` holds `private val central: CentralManager`; and
      `CentralManager.stopScan()` takes **no arguments**, because a `CBCentralManager` has exactly one
      scan. So two concurrent Kable `Scanner`s share one central, and B's stop plausibly stops A's
      scan. **The start direction may be worse than the stop:** starting a scan with different
      `serviceUUIDs` on the same central *replaces* the scan parameters, so B starting a filtered scan
      could silently narrow what A sees rather than erroring.
    - **JVM/btleplug — unclear.** `BtleplugScanner` drives a per-scan `CancellationHandle`, which
      suggests the Rust side multiplexes rather than sharing one global adapter scan. Not confirmed.
    - **Android — expected to be fine.** Each Kable `Scanner` registers its own `ScanCallback`, and
      the platform stops only that callback.

    **Untested on hardware.** Rig A case 3 (two-client authorization) had client B scan, but never had
    *both* clients scanning with one of them stopping, so this specific interaction has never run. The
    test is cheap and needs no new instrument: two `:e2e-runner:scanRun` clients against one agent,
    stagger their windows so one stops while the other is mid-scan, and check whether the survivor
    keeps receiving advertisements. Run it against the iOS agent first, since that is where the shared
    `CBCentralManager` makes interference most likely, then the JVM agent to see whether the two
    backends diverge.

    This matters more than its band suggests: "single agent, multiple clients" is a headline property
    in [design-decisions.md](../design-decisions.md), and per-client scan isolation is part of what
    that promises. If Apple cannot honour it, the honest options are to reference-count scans in
    `EngineBleBackend` (keep one platform scan alive while any client wants one, and re-issue the union
    of filters) or to document the limitation per platform.

    Two corrections to the analysis above, from verifying it against Apple's documentation:

    - **The start direction is documented, not inferred.** Apple's
      `scanForPeripherals(withServices:options:)` reference states that when a central is already
      scanning and receives another set of scan parameters, the new set overrides the previous one.
      So "B silently narrows what A sees" is stated platform behaviour. The stop direction remains
      inference from `stopScan()`'s signature.
    - **`agent-rs` already multiplexes; the Kotlin agent does not.** Its `start_scan` reference-counts
      subscribers in an agent-wide `active_scans` map, runs **one** unfiltered adapter scan, coalesces
      identity before fan-out and filters per subscriber. So this is a live **parity defect** that
      [agent-parity-verification.md](../agent-parity-verification.md) recorded as matching, not only a
      platform defect — and it closes the "does btleplug multiplex?" question by inspection, since
      `agent-rs` never opens a second adapter scan.
    - **"Apple hosts" is not only iOS.** macOS is more permissive about background execution,
      unfiltered scanning and duplicate delivery, but none of those differences touch the
      one-scan-per-`CBCentralManager` constraint — so a macOS-hosted agent is exposed to the same
      defect, and the Mac agent is not a mitigation. Whether it bites there in practice still depends
      on whether btleplug opens one central per scan or one per adapter, which is unmeasured.

22. **The two btleplug ATT-error gates are CoreBluetooth-specific, not btleplug-wide.** Found by
    Rig D, 2026-08-03; P3 (evidence integrity), not a defect. **CLOSED 2026-08-04.**

    Both gates are now keyed on the agent's *host* via `REMOTE_BLE_E2E_AGENT_HOST`
    (`macos` gated, `linux`/`android`/`ios` ungated), replacing `REMOTE_BLE_E2E_BTLEPLUG` — which
    asked about the library when the defect belongs to one of its backends, and so wrongly excused a
    Linux agent from an expectation it actually meets. The reason strings name CoreBluetooth and cite
    Rig D's contrary BlueZ result. Unset, the switch guesses from the *runner's* OS and the run now
    **prints which way it resolved**, so a defaulted gate cannot pass unnoticed. Live guidance in
    [bringup.md](../bringup.md) is rewritten with a per-backend table (Android still
    unverified), and dated corrections are added to the Rig A and Rig B evidence docs rather than
    editing their recorded readings.

    Worth keeping: this was a two-step generalisation, and each step looked reasonable. Rig A saw the
    failure on macOS and wrote "btleplug". Rig B distinguished Apple-native Kable from btleplug and
    concluded "genuinely btleplug-specific" — narrowing the claim while still keeping it one level
    too wide, because the rig had no third backend to separate the library from its Apple backend.
    Only Rig D, on BlueZ, could. **A gate is only ever evidence about the configurations you have
    actually run**, and both rigs wrote theirs as if it were about the library.

    `Main.kt` gates two live-E2E steps as expected-to-fail on *any* btleplug-backed agent, citing
    Rig A hardware evidence: `BTLEPLUG_ATT_ERROR_GAP` (a write-with-response answered by an ATT
    error never completes, so the agent reports `TIMEOUT` instead of `WRITE_FAILED`) and
    `BTLEPLUG_WRITE_POISONING` (after one such error, write completions stop for the rest of the
    connection; only reconnecting recovers).

    **Both XPASSed on Linux/BlueZ, reproducibly across two runs.** `WRITE_FAILED` was delivered
    correctly, and the next write succeeded without a reconnect. So neither gap belongs to btleplug;
    both belong to **btleplug on CoreBluetooth** — the only backend Rig A could reach. The gates have
    been over-claiming from one backend's evidence, in exactly the wording (`btleplug does not…`)
    that made them look general.

    Deliberately **not** changed in that session: narrowing a gate is a decision that wants its own
    commit and a re-read of the Rig A evidence, and doing it in the middle of a hardware run would
    have mixed a documentation change into a validation result. The runner already prints
    `NOTE: an XPASS means a backend gate is stale — re-check it and drop the gate`, so nothing is
    silently lost. The fix is to make both gates conditional on the *host*, not on btleplug, and to
    say so in [bringup.md](../bringup.md), whose "known failure on btleplug-backed
    agents" section carries the same over-broad claim.

23. **A test suite with no bound on any wait hid a real protocol defect for days, as silence rather
    than as a failure.** Found 2026-08-04; **CLOSED 2026-08-04**, root-caused and fixed on both
    sides. Two separate defects, and the order they surfaced in is the lesson.

    **The instrument.** `ScanConcurrencyWebSocketTest` drove every receive through
    `while (true) { socket.incoming.receive() }` with no timeout — 72 unbounded blocking call sites
    against 7 bounded — inside bare `runBlocking` bodies. A frame that never arrived did not fail the
    test; it suspended `:client-sdk:jvmTest` forever. No workflow had a `timeout-minutes`, so the job
    held a runner until someone cancelled it. Three jobs across two PRs were killed at 44, 65 and 178
    minutes, each stopping at that task with **nothing naming the test**, which is why it read as
    flaky infrastructure. The sibling `WebSocketEndToEndTest` is larger and bounds every receive, so
    the convention existed and this file did not follow it.

    Fixed by routing every receive through one `bounded()` wrapper that names the wait it timed out
    on (mutation-checked: cutting the bound to 1 ms fails with `timed out after 1ms waiting to open a
    client session for 'scan-a'` rather than hanging), a `timeout-minutes` on all 25 jobs, and
    archiving Kotlin test reports on failure — without which a failing assertion's message dies with
    the runner.

    **What it was hiding was a wire-contract defect, not a test bug.** With the bound in place the
    failure named `scanConc03LateJoinReceivesReplayWithinTheWindow`, and the archived report showed
    the shape: the late client got its `ServerHello` *and* its `ScanStart` `Reply`, then nothing.
    The agent was writing a scan's first `ScanResult` **before** the reply that accepts the scan —
    admission enqueues the replay cache and starts the collector inside the command handler, so the
    collector could reach the socket first. The test's `receiveReply` discarded non-matching frames,
    so it swallowed the replayed advertisement and then waited for one that was never coming again.

    Both halves are fixed: the helpers demultiplex by type and cid like a real client, and **both
    agents now acknowledge a stream before delivering to it** — `BleAgent.replyThenDeliver` in
    Kotlin, a parked arbiter mailbox plus a gated sender for `uncontrolled` in `agent-rs` — with the
    MUST written into [agent-conformance-spec.md](../agent-conformance-spec.md) §7.

    **Three things worth carrying forward.**

    - **A one-per-run signal cannot settle a coin flip.** Every ordinary CI run executes the test
      once and it failed about half the time, so `main` going green proved nothing; three greens is
      what luck looks like. A dispatch-only workflow that ran the class 30 times on a hosted runner
      turned a multi-day wait into one answer: **12/30 before the fix, 0/30 after.** It has since
      been deleted — recreate it from this entry if a flake ever needs the same treatment.
    - **It never reproduced locally**: 40 Gradle runs plus 150 iterations of the scenario in one JVM,
      all green on Apple silicon, with the harness mutation-checked so the negative was a real
      negative. Two cores versus fifteen was the whole difference.
    - **The first fix was wrong, and said so at the time.** `ScanOutboundArbiter`'s worker died
      permanently on any `emit` failure, silently ending scan delivery while replies kept working —
      the exact symptom signature. It is a genuine defect, now guarded and pinned by two
      mutation-verified tests, but it was **not** the cause. The debug tracing added to catch the
      next occurrence also emitted nothing, because `Logger` defaults to silent and no test
      configures it. What actually cracked it was reading the test helper.

24. **`peripheralStateRun`'s link probe reads the wrong characteristic, and reports a false
    negative that looks exactly like the defect under test.** Found 2026-08-04 during the macOS
    re-check of Rig D's finding 1; P3 (evidence integrity), not a product defect.

    `PeripheralStateMain` picks its probe target as
    `services.flatMap { characteristics }.firstOrNull { it.properties.read }` — the first readable
    characteristic across **all** discovered services (five on this peripheral), not the profile's
    `READABLE` one. On the test peripheral that lands on a pairing-gated characteristic, so the read
    blocks on an OS pairing prompt, never completes, and the agent correctly reports `TIMEOUT` at
    `GATT_OP_TIMEOUT`. An operator running headless — the normal case — declines or never sees that
    prompt, so **the probe times out every time**.

    **Why it matters more than a flaky probe:** the symptom is `ATT transaction did not complete;
    reporting TIMEOUT op="read"`, which is indistinguishable from finding 1's own failure mode. It
    reproduced on both attempts and was on its way to being recorded as "the Rig D fix regressed
    reads on CoreBluetooth". What settled it was running a *different* instrument against the same
    agent and the same live link: `:e2e-runner:jvmRun` reads the characteristic the profile actually
    names, and passed. Same lesson as the Rig A method notes — when an instrument and a subject can
    produce the same reading, change only the instrument.

    `Main.kt` already carries the rule this probe is missing: reading the encryption-required
    characteristic "triggers OS pairing (needs on-device user interaction), so this headless runner
    only confirms it's exposed, never reads it." **Fix:** select the profile's `READABLE` UUID
    explicitly rather than the first readable characteristic encountered, and say in the output
    which characteristic was chosen. Until then, use `jvmRun` for anything that turns on a read
    succeeding, and read `peripheralStateRun`'s probe lines as unreliable.
