Case 4 (the one case needing an operator tap): `Stop` releases the radio correctly — and, unlike the
kill in case 5, actually notifies the client (`peripheral -> Disconnected` plus a
`ConnectionState(DISCONNECTED)` wire event) — but **leaves the WebSocket server listening and
authenticating**. Zero of the inbound probes across a 240 s window were refused, ~187 s of it after
the tap. `AgentRunner.stop()` closes the Koin graph and nothing else; the module declares no
`onClose` for `AgentWebSocketServer`, which is not `AutoCloseable`, so its `stop()` is never called.
The desktop agent escapes this only because `Main.kt` calls `server.stop()` explicitly.
`AgentStopResult.serverStopped` infers its value from `graphClosed` and therefore reports `true`
wrongly. **This also root-caused the Stop → Start crash carried since the night session** (gap 8):
the restart's bind hits `EADDRINUSE` on the orphaned listener, asynchronously on a CIO worker with
no handler, so Kotlin/Native aborts — captured with a full stack this time. Operator-confirmed that the app was showing the **`Start`** button afterwards — so the
button, the runner state and the stop result all tell the user the agent is off while it keeps
accepting authenticated connections, which is what makes this a safety issue rather than an untidy
teardown. This is `mobileMain`/`commonMain` — **`android-agent` is affected identically** (untested
there, but there is no iOS-specific code on the path). See gap 14.

Case 3: a backgrounded agent that holds a BLE link stays *fully* reachable — 92/92 GATT reads and
38/38 brand-new inbound connections accepted across 91 s backgrounded, nothing degraded. The cause
is our own `UIBackgroundModes: bluetooth-central`, which keeps the process (and therefore its Ktor
accept loop) alive. A `nolink` control run — same instrument, same stimulus, only the BLE link
removed — was suspended ~8 s after backgrounding, which is what makes the result attributable. The
caveat is therefore right only for an *idle* agent and wrong for the case that matters; three
strings overstate it (gap 12).

Case 5: killing the agent mid-operation tears down cleanly on the client side (typed
`TRANSPORT_LOST` on every op, no hangs, no crash) but **leaves the BLE link up** — the peripheral
still counted the central connected 90 s later, confirmed independently by the peripheral app's own
log and `dumpsys bluetooth_manager`. Also surfaced that the client's `Peripheral.state` never leaves

16. **Asynchronous bind failures are unreportable** — **FIXED 2026-07-29 (evening); verified on
    Android hardware.** `AgentWebSocketServer.start()` is now `suspend` and does not return until

    **Awaiting `resolvedConnectors()` was necessary but not sufficient**, which only the hardware

    | Platform | How a bind failure arrives |
    |---|---|

    | Android | the accept job fails **on a `DefaultDispatcher` worker** after `start()` returned — reaching the *thread's* uncaught handler and killing the app |
    | Kotlin/Native | same asynchronous shape; the `SIGABRT` Rig B recorded |

    could observe the failure — the process was already gone. Note also that a failed CIO bind
    arrives as a `CancellationException`, so the reflex "rethrow cancellation" would silently
    restore the original defect; the discriminator is whether the *caller's* job is still active.

17. **Neither agent notices Bluetooth being switched off** (Rig B case 6, finding 9) — **FIXED
    2026-07-29 (evening); verified on Android hardware, iOS implemented but unverified.**

    Decision taken first, as the priority table asked: the wire carries a **gated event plus a new
    error kind**, not UI-only. `AgentEvent.RadioState` (capability `radio.state`) reports
    `ON`/`OFF`/`UNAUTHORIZED`/`UNSUPPORTED`/`UNKNOWN` at handshake and on every transition, and
    `ErrorKind.RADIO_OFF` answers `ScanStart`/`Connect` while the radio is unusable. Both are gated
    on the capability — an unknown enum name would fail a v1 client's decode — so an old client
    keeps the exact pre-0.10.0 behaviour.

    **Not built on Kable's `Bluetooth.availability`**, which looked like the obvious answer and is
    `@Deprecated` in 0.43.1: *"has inconsistent behavior across platforms. Will be removed in a
    future release"* (JuulLabs/kable#737). The platform APIs the original gap text named are used
    directly instead — `BluetoothAdapter` + `ACTION_STATE_CHANGED` on Android,
    `CBCentralManager.state` on Apple — behind one process-wide `AgentRadio` source shared by the
    backend and the UI, since the UI must warn while the agent is *stopped* and the backend only
    exists while it runs. The JVM/btleplug backend returns `null` and does not advertise the
    capability: it cannot see its adapter, and a constant `ON` would be a lie rather than a default.

    Six mutation-checked tests in `BleAgentTest` (three mutations run, each killing exactly one
    test). **Verified on the Pixel 8**: the UI notice appears and clears live with the agent
    stopped, and a client over the wire saw `ON` → scans accepted → `OFF` → `RADIO_OFF` → `ON` →
    accepted, driven by real adapter toggles.

    **Verified on the iPhone 14 too (2026-07-29 evening), on the second attempt — the first found a
    real defect in the Apple implementation.** `CBCentralManager` holds its delegate *weakly*, and
    the returned `StateFlow` captured nothing that referenced it, so the delegate was deallocated
    as soon as `agentRadioStateSource` returned. The failure mode is the dangerous one: the
    **initial** state still arrives (the callback fires while the local reference is alive), so it
    looks wired up, and then no transition can ever follow. First run: `radio -> ON` at handshake,

    did not. After retaining it for the process lifetime: `ON` → `OFF` (13 s later) → 7 × `RADIO_OFF`

    Note this is a defect **no JVM or Android test could have caught** — it is a property of
    Objective-C reference semantics, and the same Kotlin source is correct everywhere else.

20. **Mobile agents never configure an operator token, so they serve no dashboard** — **FIXED
    2026-07-30.** The previously recorded reason for it was also wrong: it was written up as
    structural, and `AgentConfig.operatorToken` is a plain `commonMain` field that `AgentModule`
    already forwards on every platform. `AgentApp` simply built `AgentConfig(bindHost = …)` and
    thereafter only `copy(authToken = …)`, so the credential stayed `null`, `dashboardRoutes` never
    registered, and `/` returned 404 — a wiring gap of the same shape as evidence follow-up 8, not an
    impossibility.

    **The fix:** an optional second masked field in the mobile UI. **Blank (the default) is exactly the
    old behaviour** — no credential, no routes, same 404 — so an existing install is unaffected;
    filled, the agent serves its read-only status surface to another device. `TokenStore` grew an
    `AgentSecret` parameter (default on the `expect`, so existing one-argument calls are untouched;
    Android's DataStore file name and client key unchanged, so a current install keeps its token).

    **Why two tokens is the right design, since the question was raised and deserves an answer on the
    record.** It is not that the dashboard is dangerous — it is read-only, four `GET` routes, no
    mutation endpoint by design. It is that **clients are deliberately isolated from each other on the
    op plane, and one shared token would undo that over HTTP.** Rig A case 3 proved the isolation on
    real radio: client B can scan, but every attempt against client A's leased device fails. The
    dashboard exposes every client's address, every lease and the activity log — recovering by HTTP
    exactly what the op plane refuses. Three supporting reasons, all already implemented: client
    tokens are distributed to app instances (many copies, higher leak odds) while the operator secret
    is one human's; `AUTH-REVOKE-01` revocation should be independent in both directions; and the two
    auth planes have separate brute-force limiters so an attack on one cannot exhaust the other's
    memory budget. `AgentWebSocketServer.init`'s `require` is the guard against collapsing them, and
    the UI now checks the same rule first so the user gets a message naming the field rather than the
    generic start-failure text.

    **The cleartext caveat is now fixed rather than documented.** The mobile agent binds `0.0.0.0`
    with no TLS proxy in front (that is Rig C's desktop recipe), and **Ktor's CIO server has no TLS
    support on Kotlin/Native at all** — verified by dumping the published iOS klib, which contains zero
    `ssl`/`tls` surface — so encrypting the mobile listener is not an option today. Rather than warn
    about it, the dashboard now answers **loopback only** unless remote access is explicitly opted
    into, mirroring `Main.kt`'s existing policy for a non-loopback bind. Non-loopback requests get
    **404** (not 403) *before* any credential is considered, so a correct token from the wrong origin
    still sees nothing and the surface is not advertised. Reach it from the device's own browser, or
    tunnel — `adb forward tcp:8080 tcp:8080` / `iproxy` — which keeps the secret off the network
    entirely. The UI switch appears only once an operator token is set, defaults off, and is
    deliberately **not persisted**: opening a cleartext high-privilege plane should be a per-run
    decision, not one inherited from a previous session.

    Worth keeping in view: **the client token has the same cleartext exposure** over `ws://` and always
    has. The operator token did not introduce a new class of problem, it raised the blast radius —
    which is why the fix is at the exposure layer rather than per-token. Rejected on the way:
    challenge-response or short-lived operator tokens, which would stop credential capture while
    leaving the response bodies (addresses, leases, log) in the clear — the appearance of a fix for
    real complexity.

    Two tests were added where the invariant lives rather than in the UI: an absent operator token
    leaves the routes **unregistered** (404, not 401 — the distinction that makes a phone agent's 404
    healthy rather than a symptom), and an operator token equal to a client credential is rejected at
    construction.

21. **Concurrent scans through one agent probably interfere on Apple hosts — untested, and this is
    reachable by a single ordinary client.** **Severity raised 2026-07-30:** first written up as a
    two-client problem, but `MAX_ACTIVE_SCANS = 16` is enforced *per client*, so one app holding two
    `RemoteScanner`s (say, one filtered for heart-rate monitors and one for thermometers — entirely
    ordinary) drives two Kable `Scanner`s against the same shared `CentralManager.Default`. If Apple
    cannot isolate them, the second scan breaks the first **with no error on either**, which a consumer
    would reasonably debug as a bug in their own code. That makes this the highest-severity untested
    item, not a multi-client corner.** Raised by the operator, 2026-07-30: if client A is scanning and
    client B stops *its* scan, does A's scan die?

    **Our layer is isolated, and that part is verified by inspection.** `BleAgent` is per-connection
    (`clientId` is "a fresh value each socket"), `scanJobs` is per-instance, `stopScan` only removes
    and cancels an entry from *that* client's own map, and `EngineBleBackend.scan` builds a **new
    Kable `Scanner` per call**. Scan ids are per-session, so two clients cannot collide on an id
    either. Nothing in the agent lets one client reach another's scan.

    **The radio layer is where it likely breaks, and it differs per platform:**
    - **Apple (the iOS agent, and any Apple-hosted agent) — expected to interfere.**
      `CentralManager.Companion` exposes `lazyDefault: Lazy<CentralManager>` and a process-wide
      `Default`; the Apple `Scanner` holds `private val central: CentralManager`; and
      `CentralManager.stopScan()` takes **no arguments**, because a `CBCentralManager` has exactly one
      scan. So two concurrent Kable `Scanner`s share one central, and B's stop plausibly stops A's
      scan. **The start direction may be worse than the stop:** starting a scan with different
      `serviceUUIDs` on the same central *replaces* the scan parameters, so B starting a filtered scan
      could silently narrow what A sees rather than erroring.
    - **JVM/btleplug — unclear.** `BtleplugScanner` drives a per-scan `CancellationHandle`, which
      suggests the Rust side multiplexes rather than sharing one global adapter scan. Not confirmed.
    - **Android — expected to be fine.** Each Kable `Scanner` registers its own `ScanCallback`, and
      the platform stops only that callback.

    **Untested on hardware.** Rig A case 3 (two-client authorization) had client B scan, but never had
    *both* clients scanning with one of them stopping, so this specific interaction has never run. The
    test is cheap and needs no new instrument: two `:e2e-runner:scanRun` clients against one agent,
    stagger their windows so one stops while the other is mid-scan, and check whether the survivor
    keeps receiving advertisements. Run it against the iOS agent first, since that is where the shared
    `CBCentralManager` makes interference most likely, then the JVM agent to see whether the two
    backends diverge.

    This matters more than its band suggests: "single agent, multiple clients" is a headline property
    in [design-decisions.md](../design-decisions.md), and per-client scan isolation is part of what
    that promises. If Apple cannot honour it, the honest options are to reference-count scans in
    `EngineBleBackend` (keep one platform scan alive while any client wants one, and re-issue the union
    of filters) or to document the limitation per platform.

    Two corrections to the analysis above, from verifying it against Apple's documentation:

    - **The start direction is documented, not inferred.** Apple's
      `scanForPeripherals(withServices:options:)` reference states that when a central is already
      scanning and receives another set of scan parameters, the new set overrides the previous one.
      So "B silently narrows what A sees" is stated platform behaviour. The stop direction remains
      inference from `stopScan()`'s signature.
    - **`agent-rs` already multiplexes; the Kotlin agent does not.** Its `start_scan` reference-counts
      subscribers in an agent-wide `active_scans` map, runs **one** unfiltered adapter scan, coalesces
      identity before fan-out and filters per subscriber. So this is a live **parity defect** that
      [agent-parity-verification.md](../agent-parity-verification.md) recorded as matching, not only a
      platform defect — and it closes the "does btleplug multiplex?" question by inspection, since
      `agent-rs` never opens a second adapter scan.
    - **"Apple hosts" is not only iOS.** macOS is more permissive about background execution,
      unfiltered scanning and duplicate delivery, but none of those differences touch the
      one-scan-per-`CBCentralManager` constraint — so a macOS-hosted agent is exposed to the same
      defect, and the Mac agent is not a mitigation. Whether it bites there in practice still depends
      on whether btleplug opens one central per scan or one per adapter, which is unmeasured.
