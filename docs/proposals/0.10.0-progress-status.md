### This session's findings (2026-07-28 afternoon Rig A continuation)

Picked up exactly where the morning session's gaps (below) left off. Three real defects found and
fixed, all only reachable by running on real hardware:

1. **Confirmed the degraded-write work, both agents — and found a regression in it.** Re-ran Rig A
   case 1: all 14 steps reached (12 passed, 2 known XFAIL) on the Kotlin agent. But the *first*
   attempt showed a step that's supposed to unconditionally pass — "WWR still returns `Ok`" —
   **failing**, because `EngineBleBackend.write()` was applying the degraded-connection fail-fast
   gate to `WriteWithoutResponse` too, which can never be affected by the write-completion wedge the
   gate exists for (WWR never awaits an ATT response). Fixed by folding `withResponse` into
   `degradedWriteRejection`'s own gate; added a regression test; re-confirmed fixed on hardware.
2. **`agent-rs` reproduces the same write-poisoning and now has the same fail-fast fix.** Confirmed
   on hardware (full 10s wait, then the plain timeout message) before porting `DegradedWrites` (a
   free-standing, unit-testable struct — `agent-rs` has no adapter/backend seam otherwise) plus
   `REMOTE_BLE_WRITE_FAIL_FAST`/`--write-fail-fast` to `agent-rs`. Re-confirmed on hardware: the
   fail-fast message now returns in ~3s instead of the full 10s. Rust test count: 74 → 80.
3. **Rig A cases 4, 6, 7, 8 all closed**, including Kotlin-agent repeats of everything that had
   only run against `agent-rs` before. Case 6 needed a new burst/ordering driver
   (`WwrBurstMain.kt`) that didn't exist; case 7 needed a new Battery/Device-Info driver
   (`HealthMain.kt`) and a health-peripheral app rebuild (20 days stale). Full detail in
   [pr8-rig-a-evidence.md](../pr8-rig-a-evidence.md).
4. **Case 5 — done, with an important scope correction.** Built and installed `:android-client` to
   get a genuinely cross-platform client (`fmt=STRING`), bridged over USB with `adb reverse`.
   Reconcile/resume was confirmed live across both a transport blip and a full agent restart — but
   investigating why the "agent restart forces a rescan" residual *didn't* reproduce led to finding
   that **genuine identifier rewriting is structurally unreachable on Rig A with any client this
   repo ships**: `HandleTranslator.needsRewrite` only synthesizes for a `UUID`/`MAC_ADDRESS` client
   format differing from the agent's own, but Rig A's agent is macOS/Kable (native `UUID`) — so
   `UUID` clients (JVM, iOS) are an identity match and `STRING` (Android) is never rewritten at all.
   Every client this repo ships hits a no-rewrite path against this specific agent. Real rewriting
   needs a `MAC_ADDRESS`-native (Windows) or `BLUEZ_JSON`-native (Linux) agent — i.e. Rig D or a
   Windows host, neither of which exist yet. Carried into `pr8-validation-plan.md`'s case 5 note.
5. **Two build/tooling gaps fixed in passing:** `e2e-runner`'s `jvmRun` didn't forward stdin when
   launched non-interactively (`Main.kt`'s operator prompts returned `null` immediately instead of
   blocking) — now explicit via `standardInput = System.\`in\``. This checkout's `local.properties`
   was missing `sdk.dir` entirely, blocking any Android-target build/install.
6. **A recurring environmental hazard, not a product defect:** macOS's BLE scan repeatedly reported
   a *stale* advertised name for a peripheral identity — persisting across app switches, a Bluetooth
   toggle, and an agent restart in one case; only clearing after "forget device" in Bluetooth
   settings **plus** a toggle. A stray Bluetooth *bond* also got accepted mid-session (a "Check
   pairing codes" system dialog) and later appeared to suppress an unsolicited-disconnect event from
   reaching CoreBluetooth. Both are why Case 2 (below) stayed unconfirmed — this rig accumulates
   radio-stack cruft over a long single session faster than expected.
