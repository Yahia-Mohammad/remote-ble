# RemoteBLE 0.10.0 — validated CI and deployment release

**Status:** complete; all workstreams landed and the hardware validation closed 25/25
([validation-plan.md](../validation-plan.md))

**Updated:** 2026-08-04

**Wire protocol:** remains v1

**Headline:** the same Kable application against real hardware or a simulated remote agent

## 1. Release intent

0.10.0 turns the existing single-agent RemoteBLE architecture into a fully validated, easier-to-run
release without changing its programming model. Application code still selects one remote endpoint at
construction and then uses ordinary Kable `Scanner` and `Peripheral` APIs.

The release completes the conformance/release foundation, productizes the radio-less JVM agent for CI,
ships a Linux Docker image for the real-radio Rust agent, performs the deferred hardware/iOS/TLS
validation, and publishes the accumulated SDK to Maven Central.

AgentProxy is explicitly not part of 0.10.0. Its future transparent multi-agent design is recorded in
[agent-proxy.md](agent-proxy.md).

## 2. Product promise

```text
unchanged Kable application code
              |
      RemoteBLE client SDK
              |
      one configured endpoint
         /             \
real agent + radio    simulated agent in CI
```

Only configuration changes between simulated CI and real hardware. No registry, route, or fleet API is
introduced into the client SDK.

## 3. In scope

1. Complete paired Kotlin/Rust baseline conformance and durable engineering/release gates.
2. Ship a versioned JSON simulation profile and JVM `SimulatedBleBackend` selected by
   `--simulate <profile>`.
3. Run a real-socket CI scenario against the simulated agent with no Bluetooth hardware.
4. Ship a multi-architecture Linux Docker image for `agent-rs` with an honest host-BlueZ support
   contract.
5. Complete and archive the deferred real-radio, iOS lifecycle, and `wss://` proxy validation.
6. Verify versioned artifacts and clean JVM/Android/KMP-iOS consumers.
7. Publish `:protocol` and `:client-sdk` to Maven Central and attach coordinated agent artifacts.
8. Update migration guidance for consumers moving from the last Central release, prominently including
   the earlier `authToken` provider API change.

## 4. Out of scope

- AgentProxy implementation or any client-side AgentRegistry/fleet API.
- Multi-agent discovery, route selection, deduplication, roaming, or failover.
- Simulation profile interpretation in Rust.
- Record/replay or an embedded scripting language for simulated peripherals.
- Docker support for real BLE on macOS or Windows.
- systemd packaging, GHCR signing/cosign, or a general deployment operator.
- New BLE operations, protocol-v2 work, richer scan filters, or shared peripheral participants.
- Background iOS agent execution.

## 5. Workstreams

### A. Conformance and permanent gates

- Complete paired adapters for auth/principal isolation, credential revocation, lease disconnect/grace
  and generation safety, frame/stream/slow-consumer limits, recovery, shutdown, liveness, and bind
  security.
- Keep operational-only scenarios explicitly classified; `TLS-PROXY-01` remains release-hardware
  evidence rather than a fake-only claim.
- Add a dedicated cross-agent conformance CI job or an equivalent clearly named task invoked by the
  main build.
- Add measured coverage reports, dependency/license vulnerability checks, secret policy, SBOMs,
  release artifact inventory, and clean-consumer verification with documented exception handling.

Exit gate: every baseline row links to paired executable evidence and every permanent gate runs on the
appropriate pull-request, scheduled, or release path.

### B. Simulated JVM agent

- Define `schemaVersion: 1` JSON profiles for advertisements, services, characteristics, static/
  sequence/counter values, notification schedules, write behavior, connection latency/failure, and
  spontaneous drop injection.
- Promote a production `SimulatedBleBackend` without coupling the normal engine to simulation code.
- Add JVM CLI/environment selection and fail fast on invalid profiles.
- Ship a canonical HRM/test profile matching the live rig where practical.
- Dogfood the feature in CI: start the real WebSocket server with the simulated backend and drive the
  ordinary client SDK through scan, connect, discover, read, write, observe, reconnect, and shutdown.

Exit gate: the same E2E client scenario passes against a simulation endpoint with no Bluetooth and a
real endpoint during the hardware round by changing only URL/credential configuration.

### C. Rust-agent Docker image

Implement the contract in [rust-agent-container.md](rust-agent-container.md):

- Linux `amd64` and `arm64` image published with the GitHub release;
- host BlueZ reached through the mounted system D-Bus socket;
- explicit `0.0.0.0` bind plus mandatory credentials for published ports;
- signal-safe shutdown, read-only runtime filesystem where supported, non-root execution if validated;
- no `--privileged` or host-network requirement unless hardware testing proves it unavoidable;
- smoke-tested on stock Ubuntu and Raspberry Pi/aarch64 before it is called supported.

Exit gate: pull-and-run instructions complete scan/connect/read against a real peripheral on both
supported host classes, and image provenance is tied to the release commit/version.

### D. Deferred validation bundle

Run the [hardware-validation gate](../bringup.md#0100-hardware-validation-gate), including:

- accumulated real-radio correctness and parity checks;
- iOS agent lifecycle start/stop/cancellation/failure recovery;
- TLS-terminating proxy with WebSocket upgrade, bearer forwarding, CA trust, reconnect, and live
  notifications;
- Rust-agent container on Ubuntu and Pi;
- secrets-redacted machine-readable evidence tied to the release commit.

Exit gate: all results are archived before tag/publication approval.

### E. Publication and consumer verification

- Bump every shipped/shown version source to 0.10.0 and pass `check-release-version.sh`.
- Build and inventory JVM fat JAR, native Rust binaries, Rust container manifests, protocol/SDK
  publications, checksums, and SBOMs.
- Resolve the release candidate from clean JVM, Android, and KMP/iOS consumers.
- Confirm Central quota/capacity and encrypted signing/publishing credentials before dispatch.
- Tag only the approved release commit, attach GitHub artifacts, publish Central once, and verify the
  actual repository contents after publication.

Exit gate: clean consumers resolve exactly 0.10.0 and the GitHub/Central artifacts agree with the tag.

## 7. Compatibility rules

- Protocol version stays 1 and no wire schema changes are required.
- Existing local/remote factories and single-agent client code remain valid.
- Simulation is agent configuration, not a client API mode.
- The Rust image runs the same `agent-rs` binary distributed directly; it is not a separate behavior.
- Agent binaries and SDK artifacts share the 0.10.0 version even where no protocol change occurred.
- Release notes distinguish changes since 0.9.1 from the migration experienced by consumers whose last
  Central version is older.

## 9. Effort and risk

Expected effort is approximately four to six solo weeks:

- conformance and engineering gates: 1–2 weeks;
- simulation backend and E2E: 1–2 weeks;
- Rust container packaging/workflow: 3–5 days plus host validation;
- RC, hardware, TLS, iOS, and publication: roughly 1 week subject to rig availability.

The main schedule risks are the breadth of unfinished conformance, BlueZ/D-Bus policy differences
between Linux hosts, and availability of the hardware/TLS/iOS validation setup. None justifies changing
the Kable-facing client API.
