# 0.9.1 hardening decisions

**Status:** accepted for 0.9.1 implementation  
**Date:** 2026-07-15  
**Scope:** security, lifecycle, and conformance hardening; protocol v1 remains unchanged.

This records the decisions required by the 0.9.1 implementation plan. Both agents must implement
the observable rules below or advertise the affected capability as unavailable. No decision requires
wire v2.

## D1 — shared peripheral access

Shared access is removed from the supported product contract for 0.9.1. Peripherals are exclusively
leased to one authenticated principal and stable-client generation. Remove dormant shared-mode
configuration, branches, dashboard claims, and documentation; do not merely hide them. A participant
lease model is deferred to a separately approved release.

## D2 — disconnect and grace semantics

| Event | Lease | Radio link | Resume |
|---|---|---|---|
| Explicit `disconnect` | Released immediately | Disconnected when released | Never automatic |
| Transport loss | Retained through transport grace | Kept warm during grace | Same principal and stable client ID only |
| Grace expiry | Released | Disconnected | New connect required |
| Radio drop | Connected state ends; lease is retained through lease grace | Already down | Client reconciliation may reconnect during grace |
| Agent restart | All state is lost | Down or unknown | Translated handles require rescan |

Explicit disconnect is never converted into transport grace. Terminal events are generation-bound: a
retired connection may not release or mutate a newer generation.

## D3 — deployment security contract

Desktop and headless agents bind loopback by default. A non-loopback bind requires an explicit bind
option and at least one client credential, unless an explicitly named development override is set.
The override emits a prominent unencrypted-service warning and is not a supported deployment mode.

Credentials are unique, non-empty named `name=secret` pairs and use constant-time comparison where
the platform supports it. `REMOTE_BLE_TOKEN` remains the `default`-principal alias through 0.9.x.
The verified credential determines the principal; `X-RemoteBle-Client` is only a bounded reconnect
generation key within that principal. Revoked credentials cannot resume warm leases. Duplicate live
generations for one principal/client key are rejected; handoff is deferred.

Phone agents require the operator to provide a credential and explicitly start LAN service. The UI
must show bind/exposure and encryption state and never silently start an open listener. The supported
encrypted deployment is a TLS-terminating reverse proxy or VPN with local-only upstream, certificate
validation, and WebSocket upgrades. Direct `ws://` is trusted-network/development only.

Client and operator credentials are separate. Management reads that disclose client, device, address,
or activity data require operator authentication. Browser-triggered management mutation remains out
of scope; any future mutation also requires Origin/CSRF protection.

## D4 — protocol incompatibility

Invalid ranges (`minVersion > maxVersion`) and no-overlap ranges close the WebSocket before normal
operation with close code **1002** and fixed reason `REMOTE_BLE_INCOMPATIBLE_PROTOCOL`. The client
maps this terminal condition to `INCOMPATIBLE_PROTOCOL`, distinct from `TRANSPORT_LOST`. The only
selectable version is v1. Kotlin and Rust share fixtures for invalid, no-overlap, and successful v1
negotiation.

## D5 — overload policy

The following are hard ceilings pending measured defaults. Lower documented defaults are allowed;
raising a ceiling requires a new decision.

| Class | Policy |
|---|---|
| Message / encoded frame | Reject above 1 MiB before decoding or repeated copying. |
| Client ID / other strings | Reject above 128 / 512 UTF-8 bytes respectively. |
| Filters / scans / observations / commands | Reject above 64 / 16 / 128 / 64 per connection. |
| Write or descriptor payload | Reject above 512 bytes pending long-write support. |
| Replies/control | Reserved bounded capacity; never silently drop. |
| Advertisements | Bounded and lossy/coalescible with counters. |
| Notifications | Bounded; overflow terminates the stream with a stable outcome. |
| Failed authentication | Per-peer and global bounded rate limiting; no unbounded peer map. |

Rejected work and overflow must have stable errors, state/metrics, and rate-limited logs. Slow
consumers must be disconnected or have their affected stream terminated promptly; they must not cause
unbounded queues or task growth.

## Compatibility and order

Existing 0.9.0 exclusive isolation and ordering behavior remains mandatory. Principal identity
precedes resource keys; bind/auth configuration precedes TLS deployment tests. Readiness/recovery and
structured-shutdown APIs remain additive during 0.9.x.
